## 1. Цель

Выпустить на PC законченную аркадную игру, которая:

1. воспроизводит механику Elevator Action (Taito, 1983) **без изменений в геймплее**;
2. выглядит современно — за счёт динамического 2D-освещения, нормал-мап и пост-обработки,
   а не за счёт переизобретения дизайна;
3. на каждом коммите проходит автоматические проверки.

Формула проекта: **механика 1983 года, картинка 2026 года.**

## 2. Definition of Done эпика

- [ ] Полный игровой цикл: вход с крыши → сбор всех документов → выход к машине → следующее здание
- [ ] 30 этажей, лифты, эскалаторы, двери, враги-агенты, стрельба, удар ногой
- [ ] Отстреливаемые лампы и затемнение этажа
- [ ] Жизни, счёт, таблица рекордов, экран Game Over
- [ ] Главное меню, настройки, поддержка геймпада
- [ ] Сборки под Windows и Linux собираются в CI по тегу
- [ ] Зелёный CI; игровая логика покрыта тестами (рендер — нет)

## 3. Границы

**Не входит в эпик:** мультиплеер, мобильные платформы, консоли, редактор уровней для
игроков, онлайн-таблица рекордов, 3D-геймплей, сюжетные вставки.

Онлайн-лидерборд вынесен в опциональный M13 — он единственный, ради чего в проекте
может появиться бэкенд и docker compose (см. [ADR-0003](adr/0003-no-docker.md)).

## 4. Механика оригинала — источник правды

Реализуем как в аркадном оригинале. Спорные детали сверяем с запуском ПЗУ в MAME,
а не по памяти.

| Механика | Суть | Веха |
|---|---|---|
| Otto | Агент 17. Ходит, приседает, прыгает, стреляет, бьёт ногой | M1 |
| Здание | 30 этажей, спуск сверху вниз, выход на первом этаже | M5 |
| Лифты | Кабина в шахте; управляется игроком изнутри; без игрока ездит сама; на крыше едут без управления; давит насмерть | M2 |
| Эскалаторы | Посадка нажатием на площадке, автоматический перенос между этажами | M2 |
| Двери | Обычные — засады, из них выходят враги; красные — в них документы; внутри прячутся до пяти секунд | M3 |
| Документы | 500 очков за штуку; выход без всех возвращает к верхней несобранной двери | M3 |
| Враги | Агенты выходят из дверей, ходят и стреляют; телом не вредят | M4a |
| Свет | Лампы отстреливаются и падают на головы; этаж темнеет | M4b + M6 |
| Финал уровня | Выход на первом этаже к машине | M5 |

**Требует сверки с оригиналом:** точное число красных дверей на здание, таблица очков за
врагов, правила респавна, поведение врагов в темноте, бонус на выходе.

Первое, во что можно играть. Графика — серые коробки, и это нормально.

- [x] `CharacterBody2D` и машина состояний: idle / walk / crouch / jump / fall / dead
- [x] Гравитация, коллизии, пол этажа, стены по краям уровня
- [x] Камера: следование за игроком, привязка к границам уровня

- [x] Ввод: клавиатура и геймпад
- [x] Тесты машины состояний (14 штук)
- [x] Снятие скриншотов вехи (`tools/capture.py M1`)

**DoD:** Otto бегает, приседает и прыгает по одному этажу; тесты зелёные. ✅

Машина состояний вынесена из узла в отдельный класс `OttoStateMachine`: она принимает
снимок ввода и факты о теле, а возвращает состояние. Благодаря этому она тестируется
без сцены и без физики.

### M2 · Лифты и эскалаторы — ядро игры

Самая рискованная веха: тут вся физика взаимодействия с движущимися платформами.
Механика сверена с оригиналом перед началом работы и зафиксирована в
[ADR-0004](adr/0004-elevator-mechanics.md).

- [x] Шахта описана данными уровня: границы и этажи-остановки. Отдельным `Resource`
      станет в M5 вместе с остальным описанием здания
- [x] Кабина: `AnimatableBody2D`, движение вверх и вниз, остановка на этажах
- [x] Вход в кабину и управление ею изнутри, выход на этаж при совпадении полов
- [x] Автономное движение кабины, когда Otto в ней нет: от этажа к этажу с паузой
- [x] Езда на крыше кабины, без управления ею (перенос игрока платформой)
- [x] Открытый проём шахты: перебегается и перепрыгивается, падение в пустую шахту убивает
- [x] Смертельное сдавливание игрока кабиной (враги — в M4)
- [x] Эскалаторы: посадка нажатием «вверх/вниз» на площадке, перенос между этажами
- [x] Контекстный ввод: «вниз» — присед на этаже и спуск кабины в шахте
- [x] Проверка свободного места над головой при вставании из приседа (долг M1)
- [x] Тесты: перенос платформой, посадка и высадка, сдавливание, падение в шахту

**DoD:** можно спуститься с верхнего этажа на нижний, используя лифт и эскалатор. ✅

Спуск снят кадрами: `python tools/capture.py M2` проходит весь маршрут вехи — вход
в кабину на верхнем этаже, спуск на нижний, подъём эскалатором на средний и падение
в пустую шахту.

- [ ] Импорт-пресеты Godot зафиксированы в репозитории
- [ ] Тесты: каждый ассет, который просит сцена, существует, делится на кадры и имеет нормаль

**DoD:** серых коробок в кадре не осталось, кроме Otto и агентов; 60 FPS держатся

### M13 · Нативный FullHD и качественные текстуры

Сейчас мир рисуется в 640×360 и троится до 1080p: пиксель крупный, а в кадр
влезает 640 px мира — меньше самого узкого этажа.

**Что показала проба** (сделана до вехи, чтобы не перерисовывать вслепую):

- Ассеты окружения описаны прямоугольниками в единицах мира, поэтому рендер
  «втрое крупнее» даёт **пиксель в пиксель то же самое**. Разрешение само по
  себе не покупает ничего.
- Прибавка есть ровно там, где картинка не нарисована руками, а посчитана:
  актёры приходят рендером из Blender, и в 3× у них появляется настоящая
  полутень на лице и складка на костюме — это бесплатно, настройкой рендера.
- Перерисованный с деталью ассет выигрывает сразу: у кладки появляются разнотон
  кирпича, фаска и сколы, у двери — профиль рамы, две филёнки, ручка с бликом
  и порог. То есть веха не про масштаб, а **про детализацию**.

Отсюда её состав: разрешение — это повод, работа — текстуры.

Веха идёт **первой из визуальных**: сделай её позже — и кадры анимаций, шахты,
эскалаторы и обстановку пришлось бы рисовать дважды.

- [x] ADR на смену визуальной цели: [ADR-0002](adr/0002-visual-target.md) описывает
      640×360 и масштаб 3×, и это решение его меняет
- [x] Вьюпорт 1920×1080, мир масштабируется втрое: высота этажа, ширина здания,
      рост актёров, скорости, прыжок — всё в пикселях и всё ×3
- [x] `render_env.py --scale` — общий масштаб холста вместо тройных чисел
      в каждом ассете (сделано на пробе)
- [x] `render_actors.py --scale` — плотность рендера при той же камере
      (сделано на пробе)
- [x] **Ассеты окружения перерисованы с мелкой деталью:** кладка с разнотоном
      и сколами, двери с профилем и филёнками, перекрытия с кромкой и швами,
      кабина с панелями, лампа с патроном и проводом
- [x] Детализация зависит от масштаба, а не дублирует ассет: генератор знает
      свой `scale` и на крупном холсте рисует то, чего в единице мира не бывает
- [x] Актёры перерендерены из Blender крупнее (ADR-0011)
- [x] Шрифты, HUD и меню пересчитаны под новый вьюпорт
- [x] Тесты: ни одно число геометрии не осталось в старом масштабе; каждый ассет
      втрое крупнее своего прежнего размера; бот проходит здание; кадр
      укладывается в бюджет 16.6 мс

- [x] Пропорции: Otto и агенты крупнее, дверь выше, окно меньше (ADR-0018, решение 5)
- [x] Предел полосы шахты виден: упоры и стрелки в кабине (решение 6)

**DoD:** игра идёт в 1920×1080 без растягивания, и на глаз она **детальнее**,
а не просто крупнее: на стоп-кадре видно кирпич, филёнку и патрон лампы.

### Пивот: с M15 проект переезжает в 3D

Решение и его цена — [ADR-0019](adr/0019-3d-pivot.md). Коротко: визуальной целью
становится 3D-сцена с ортокамерой сбоку вместо 2D-кадра из спрайтов. Логика игры
не меняется ни в одном правиле; меняются слой узлов, пайплайн ассетов и свет.

Три вещи задают форму всех вех ниже:

- **Каждая веха заканчивается играбельной сборкой.** Первая даёт коробки, а не
  красоту (ADR-0019, решение 4). Пока 3D не проходит бота — `main` остаётся
  на 2D-сборке и остаётся собираемым.
- **Читаемость аркады важнее кинематографичности.** Игровой объект не имеет права
  зависеть от освещения сцены (решение 5). Кадр с погашенными лампами снимается
  в каждой вехе наравне с освещённым.
- **Механика не живёт в узле.** Если новое правило оказалось в `_physics_process`,
  оно написано неправильно: решение принимает класс без сцены, узел его исполняет.

### M14 · Дверь открывается по-настоящему

Единственная веха до пивота, и она про поведение, а не про картинку. Игра сыграна
руками, и первое, что видно: агенты появляются **поверх закрытой двери**, а двери
при этом не открываются вовсе. Это баг логики — он переживёт смену рендера и
воспроизведётся в 3D один в один, только чинить его там будет дороже: рядом уже не
будет работающей игры для сравнения.

- [x] Цикл двери выносится в класс без узла (`DoorCycle` на `RefCounted`):
      `closed → ajar → open → closed`, с временами и запретом выпуска. Тогда
      веха переезжает в 3D бесплатно
- [x] Дверь не отдаёт агента, пока не открылась, и закрывается за ним
- [x] Агент выходит из проёма шагом, а не возникает на коврике: пока створка
      идёт, его не видно
- [x] Ход двери плавный и для Otto: у `DoorVisit` есть `open_time`, но картинка
      о нём не знает
- [x] Тесты: дверь не выпускает агента раньше, чем открылась; за вышедшим
      закрывается; цикл проверяется без сцены

**Чего в вехе нет:** кадров анимации. Ходьба в три кадра и прыжок в один
переделываются не дорисовкой спрайтов, а моделью с анимацией — это M16.

**DoD:** ни один агент не появляется поверх закрытой двери, и цикл двери
проверяется тестом без сцены.

### M16a · Цена приседа: агент, стреляющий с колена

Припаркована 2026-09-20: механика решена, но делать её решено не сейчас — приоритет
у переезда в 3D. Сюда она попала потому, что новому типу нужна модель, а модели
появляются в M16.

**Зачем:** пуля агента всегда идёт в 105 px над полом, а присевший Otto ростом 81.
Значит присевшего не берёт вообще ничто — ни один агент, ни сколько угодно их разом.
Единственное, что наказывает за отсидку, — сирена. Это открытый вопрос №7.

**Расхождение с оригиналом, принятое сознательно:** в 1983 низкий выстрел умеет тот же
самый агент — «agents can crouch under your standing bullets just as you can crouch
under theirs», и низкий выстрел Otto по ним не уклоняется вовсе. Мы вместо этого
заводим отдельный тип: по силуэту должно быть видно, от кого присед не спасёт.

Решено (2026-09-20):

- [ ] Отдельный тип агента, обычные агенты не меняются
- [ ] Силуэт: каска и рост ниже обычного. Перекраски мало — на погашенном этаже цвета
      почти нет, и силуэт единственное, по чему игрок отличает своего от чужого
      ([ADR-0011](adr/0011-asset-pipeline.md), пункт 13)
- [ ] Поведение: стационарный стрелок — занял колено у своей двери и держит сектор,
      не преследует. Otto получает задачу обойти, а не пересидеть
- [ ] Появление: с первого здания, доля растёт со злостью, как `agent_menace`.
      Делит общий потолок в восемь живых
- [ ] Числа — в `BuildingRules`, а не в сцене (ADR-0016, пункт 5)
- [ ] Цена замеряется ботом, а не на глаз, — как телеграф двери в M14
- [ ] ADR на веху: расхождение с оригиналом и выбор стационарного стрелка

**DoD:** присевший Otto перестал быть неуязвимым, и по кадру видно, кто именно
его достанет.

### M17 · Свет, материалы и читаемость

Свет — то, ради чего переезд и затевался. Отзыв был «свет нужен более красивый
и мягкий»; ниже разложено, из чего эта мягкость складывается в 3D.

- [ ] PBR-материалы: шероховатость и металл вместо диффуза с нормалью.
      Проба показала, что свету нужна геометрия — фаски, торцы, ребро
- [ ] Источники с мягкими тенями, спад физический, температура разведена:
      лампа тёплая, окно холодное, шахта своя
- [ ] Объёмный туман и свечение — плотностью намёка, а не молока: на 0.015
      конусы ламп съедали весь кадр (ADR-0019, проба)
- [ ] Отражения в полу. Упирается в наклон камеры: строго сбоку пол не виден
      вовсе. Наклон подбирается пробой, при ограничении решения 6 —
      пуля летит в плоскости XY независимо от камеры
- [ ] Контактные тени под актёрами: без них они кажутся наклеенными
- [ ] Лампа на подвесе: шнур, патрон, качание после выстрела
- [ ] **Читаемость:** дверь, документ, лампа, кабина и агент получают
      собственную светимость или контур и остаются видны на погашенном этаже
- [ ] Тесты: кадр укладывается в бюджет 16.6 мс; на кадре с погашенными лампами
      виден каждый объект, с которым игрок взаимодействует

**DoD:** свет выглядит мягким и объёмным, и при этом на тёмном этаже игрок
видит, во что стреляет.

### M18 · Геометрия здания: силуэт, шахты, эскалаторы

Ниже двадцатого этажа на этаже одна шахта, и выбора, куда ехать, нет. Эскалатор
нарисован голой ломаной. Верхние этажи шире кадра. Всё это переехало сюда из
2D-плана: в 3D эскалатор и шахта строятся геометрией, и делать их дважды незачем.

Сверка: [Elevator World](https://elevatorworld.com/article/elevator-action/) разобрал
здание оригинала как настоящее — шахты там неравные и пересекающиеся (10–12, 13–15,
15–17, 19–30 с крышей), этажи 17–20 обслуживаются двумя эскалаторами каждый, а в двух
шахтах ходит двухэтажная кабина. Мы берём из этого не буквальную раскладку, а вывод:
**чем ниже, тем больше путей**.

- [ ] Силуэт задаётся порогом, а не равными ступенями: широкая часть начинается
      с этажа N (по умолчанию 20), выше — узкая
- [ ] Верхние этажи влезают в кадр целиком, нижние десять — шире экрана, как
      и просил игрок
- [ ] Шахт на этаже: наверху одна, в середине две, внизу три. Полосы остаются
      равными — неравные и пересекающиеся тянут за собой весь граф достижимости
- [ ] На стыках полос внизу — по два эскалатора, как в оригинале
- [ ] Эскалатор строится конструкцией: балюстрада, ступени, площадки, обрамление
      проёма. Сейчас это `Line2D` с тайлом
- [ ] Тесты: на любом сиде этажи выше порога влезают в кадр, а ниже — нет;
      число шахт на этаже растёт книзу; бот по-прежнему проходит любое здание

**DoD:** с двадцатого этажа и ниже в кадре всегда есть выбор, куда ехать, а
эскалатор выглядит эскалатором, а не линией между этажами.

### M19 · Наполнение и задний план

Этаж пустой: голая стена, окна и двери. Кадру не хватает не света, а глубины
и мусора жизни. Проба показала это прямо: ритм пилястр и пара предметов дали
больше, чем любая настройка источников.

- [ ] Задний план: слои города с настоящей глубиной вместо параллакса
      прямоугольниками, силуэты ближе — темнее, дальше — размытее
- [ ] Небо и погода раунда: дождь, туман или ясная ночь — раз на здание, заодно
      отличая раунды не только цветом
- [ ] Обстановка этажа: конторская мебель, трубы, вывески, кадки, автоматы —
      то, мимо чего Otto бежит
- [ ] Мелочи здания: номера этажей, табло у шахт, таблички
- [ ] Палитра раунда возвращается материалами и температурой света
      ([ADR-0017](adr/0017-spectrum-palette-and-shafts.md) в части приёма, не цветов)
- [ ] Тесты: обстановка не встаёт на места, занятые шахтой, дверью или лампой,
      и не мешает проходимости; читаемость на погашенном этаже держится

**DoD:** по кадру видно, что это здание ночью в городе, а не схема здания.

### M20 · Грейдинг и полировка

Последняя веха пивота: то, что делают, когда всё остальное стоит на местах.

- [ ] Тонмаппинг, экспозиция и цветокоррекция подбираются на готовой сцене
- [ ] Глубина резкости — если она не мешает читаемости, и ровно настолько
- [ ] Полосы на градиентах убираются дизерингом
- [ ] Бюджет кадра проверяется на полном здании, а не на трёх этажах
- [ ] 2D-ассеты и системы, оставшиеся без читателей, удаляются
      (ADR-0019, решение 8)

**DoD:** кадр можно поставить рядом с референсом и говорить о разнице в ремесле,
а не в возможностях.

### M21 · Онлайн-лидерборд (опционально)

Единственная часть, где появится бэкенд и docker compose. Была M13, потом M18 —
переезжала дважды, каждый раз когда находилась работа по визуалу;
[ADR-0003](adr/0003-no-docker.md) говорит о ней под первым номером.

- [ ] API, БД, docker compose
- [ ] Клиент в игре, минимальная защита от накрутки
- [ ] Деплой

## 6. Сквозные требования

| Требование | Как проверяем |
|---|---|
| Типизированный GDScript везде | `gdlint` и ревью |
| Единое форматирование | `gdformat --check` в pre-commit и CI |
| Логика покрыта тестами | GUT, прогон в CI (начиная с M1) |
| 60 FPS | Профилирование в конце M5 и M6 |
| Нет ошибок импорта и разбора | `tools/godot_check.py` на pre-push и в CI |
| Геймпад работает наравне с клавиатурой | Ручная проверка в конце каждой вехи |
| Русский и английский интерфейс | M8 |
| Скриншоты каждой играбельной вехи | `tools/capture.py <веха>` → `screens/<веха>/` |
| Авторевью изменений после каждой вехи | `/code-review xhigh --fix` до открытия PR |

### Скриншоты вех

После каждой вехи, в которой игру можно запустить, снимаем кадры для анализа и сравнения
с предыдущими вехами:

```powershell
python tools/capture.py M1
```

Игра запускается с аргументом `--capture=M1`, автолоад `Screenshotter` прогоняет короткий
сценарий (стоим, идём, прыгаем, приседаем), сохраняет по кадру на шаг и закрывается.
Кадры ложатся в `screens/<веха>/<время>_<шаг>.jpg`. Папка `screens/` не versions —
это локальный материал, а не часть репозитория. Вручную кадр снимается клавишей **F12**.

### Авторевью

Перед тем как открыть PR по вехе, изменения прогоняются через авторевью повышенной
тщательности с автоматическим применением исправлений:

```
/code-review xhigh --fix
```

Найденные проблемы правятся сразу, после чего заново гоняются `tools/check.ps1` и тесты.
Результат ревью кратко фиксируется в описании PR.

## 7. Процесс работы

- **Ветки:** `feat/m2-elevators`, `fix/elevator-crush`, `chore/ci-cache`. В `main` напрямую не пушим.
- **Коммиты:** Conventional Commits — `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.
- **Перед коммитом:** хуки прогоняются сами. Вручную — `tools/check.ps1`.
- **Перед push:** дополнительно прогоняется проверка движком и тесты.
- **В конце вехи:** снимаем скриншоты, гоняем `/code-review xhigh --fix`, повторяем проверки.
- **PR:** один PR на веху или на крупную задачу внутри вехи, merge только при зелёном CI.
- **Решения:** всё, что влияет на архитектуру, оформляется как ADR в `docs/adr/`.
